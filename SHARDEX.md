# PROJECT SHARDEX

Mirror a game's entire codebase, shatter it into shards, and transubstantiate a shard
into **FLAME** — a playable 3D arena whose parameters are generated from that shard, with
a golden state hash that the browser and the tool both agree on.

```bash
python Project_SHARDEX/shardex.py --mirror /path/to/game            # L0
python Project_SHARDEX/shardex.py --shatter --out /path/to/game     # L1
python Project_SHARDEX/shardex.py --forge .shardex/shards/<name> --out flame   # L2
python Project_SHARDEX/shardex.py --golden .shardex/shards/<name>  # the expected hash
python Project_SHARDEX/shardex.py --verify flame                   # does the bundle agree
python Project_SHARDEX/shardex.py --doctor
python Project_SHARDEX/shardex.py --selftest                       # 13 checks
```

Stdlib only. No key, no build, no network.

## The ladder, and where it actually stands

| rung | what it does | state |
| --- | --- | --- |
| **L0 MIRROR** | walks the game's tree once, sha256 per file, role per extension, provenance per file, refuses a source that is not there or holds nothing | **BUILT** |
| **L1 SHATTER** | cuts the mirror into self-contained, content-addressed shards (`name@sha256:<64>`), one per top-level group, bounded by the 24-file / 2 MiB low-end ceilings | **BUILT** |
| **L2 FORGE** | transubstantiates one shard into `flame.json` + `flame.html`: a 3D arena whose size, orb count and seed come from that shard's own content hash, with a golden run computed in Python and in the browser | **BUILT** |
| **L3 TUNE** | a champion edits `flame.json` (or forges with `--tune k=v`); the golden hash moves with the config, so every bracket has a hash it must agree on | **BUILT** |
| **L4 LAUNCH** | brackets, signed result files, replay verification, entry fees, a spectator view | **BUILT** |
| **L5 COMPOSE** | two or more forged meshes into one arena, with a composition hash that is a property of the set — order-independent, byte-sensitive, and refusing a rule the inputs disagree about until it is declared | **BUILT** (2 lanes measured; see below) |

## The honest boundary — read this before the marketing writes itself

**FLAME is a playable 3D arena whose parameters are generated from a shard. It is not the
original game's mechanics.**

Extracting a ruleset from arbitrary source code is a research problem. A tool that printed
"your game, resurrected" over a generic arena would be exactly the defect this estate
keeps paying for: a true-looking claim with nothing behind it. What *is* real:

- the arena is **derived** from the shard — `arena` from payload bytes, `orbs` from file
  count, `seed` from the content hash — so two shards forge two different arenas;
- `flame.json` names the shard it came from, and the shell prints that id on screen;
- the golden run is a number — `1f046312729509fc` for the METTHEW `highend_duel` shard as
  it stands today — that Python and Chrome both compute from the same scripted input.
  The figure this page used to quote, `1c045e596f950543`, is the golden of the
  **tournament-surface config below** (`arena 8.07`, seed `4220286397`), not of this
  clone: editing `SHARD.md` in `d69d047f` changed its `size_bytes`, which moved the
  seed, which moved the orbs, which moved the number. Both figures are real; only one
  of them is this shard.

So the claim SHARDEX makes is: *this shard, at this config, produces this deterministic
arena, and the artifact you are holding is provably that arena.* It does not claim to be
the game the code came from.

## Why a golden hash and not a screenshot

"Playable" is not a test. A state hash is:

- fixed-step sim at `sim_hz`, floats in doubles, the same expression order in both
  languages;
- a **scripted** input (right for 60 ticks, left for 60, jumps at 10 and 70) — an input
  generated by the thing under test would prove only that the generator is consistent
  with itself;
- the state serialised to 4 decimals and hashed with two FNV-1a 32-bit lanes → 16 hex
  characters, because `Math.imul` reproduces the 32-bit product exactly where a 64-bit
  hash would need BigInt and invite a silent divergence;
- orbs placed by an LCG seeded from the shard, spelled out identically in both languages,
  because `Math.random()` would make every browser a different game.

- **it is a reading, not an identity.** Measured 2026-11-02 at the default tunables:
  seeds `999` and `424242` both produce `1b045cc66e9503b0`, because the scripted sweep
  only crosses the orbs that happen to lie on its path. So a bracket compares
  `(golden, shard id)` and never the hash alone — SHX-R4 inherits this caveat rather
  than a cleared premise.

### Plays in one file, with clicks (SHARDEX-BROWSER-PLAY, 2026-11-02)

`flame.html` references nothing: no `script src`, no stylesheet, no font, no image — the
whole arena is one file and a browser, so "zero install" is a property of the artifact
and not of the machine. Input is keys (`A/D`, arrows, space) *and* the pointer: a click
is unprojected onto the ground plane through the same camera `draw()` uses, so the cube
walks to the patch of floor that was clicked, and hops once. Nothing in the pointer path
touches the golden run, which is why a human can play in the arena a bracket still agrees
on. `?probe=clicks` dispatches real `PointerEvent`s and publishes `data-probe="PASS"`
only when a click moved the player *and* left `data-hash` unchanged;
`tests/test_shardex.py::test_the_arena_is_one_file_and_a_click_moves_the_player` runs it
under headless Chrome.

Re-measured 2026-11-02 on `docs/METTHEW/reference-shards/highend_duel`:
`--golden` → **`1f046312729509fc`**, final state `-0.0000,0.0000,0.0000,0.0000,0.0000,4`.
The earlier reading, `1c045e596f950543`, does not reproduce from this clone in either
implementation — it is the golden of the `arena 8.07 / seed 4220286397` config, so a
browser figure recorded against it says nothing about the shard as it is now.

Re-forged and re-read in a browser the same day: `--forge` wrote `build/tmp/refgold`, and
headless Chrome's dump of that page carries `data-hash="1f046312729509fc"`,
`data-expected="1f046312729509fc"` and `golden: 1f046312729509fc OK` — Python and the page
agree on this shard, not only on a fixture. The standing test for that agreement is
`tests/test_shardex.py::test_the_browser_computes_the_same_golden_hash_and_can_play`,
which forges a shard from the fixture game and is skipped when no browser is present.

### The golden run, stated completely (SHX-R1, 2026-11-02)

The five bullets above fixed the *shape* of the hash and left the law unwritten. A third
implementation written against them had to supply **21 constants that appeared nowhere in
this document** — the simulation itself was the missing part, not the quantisation. They
are stated here so the next port needs nothing but this page and `shard.json`.

**Tunables, derived from the shard (`_tunables_for`).** Defaults `sim_hz=60, gravity=18.0,
speed=6.0, jump=7.0, arena=12.0, orbs=6, difficulty=1.0, seed=1`, then overwritten:

| field | law | `highend_duel` |
| --- | --- | --- |
| `arena` | `round(8.0 + min(12.0, payload/200000.0), 2)` | 8.06 |
| `orbs` | `max(3, min(12, len(files)))` | 3 |
| `seed` | `int(id_sha256[:8], 16) or 1` | 3926918967 |
| `difficulty` | `round(1.0 + min(2.0, len(files)/24.0), 2)` | 1.08 |

`payload` is `sum(size_bytes)`. **`difficulty` is in the config and in no equation — the
simulation never reads it**, so for the purposes of the hash it is decoration. Stated
because an ignored parameter is a mutation that quietly did less than its author believed.

**The tick, in this exact order** (`dt = 1/sim_hz`, ticks `120`, jumps at `10` and `70`;
`x = y = z = vy = 0.0`, `collected = 0` at tick 0):

1. `ix = +1.0` while `tick < ticks//2`, else `-1.0` — right for 60, left for 60.
2. if `tick in jumps` **and** `y <= 0.0001`: `vy = jump`. The test comes before the
   integration, against `y` as it stood at the end of the previous tick.
3. `x += ix * speed * dt`; `z += 0.0`.
4. `vy -= gravity * dt`.
5. `y += vy * dt`.
6. wall: `if y < 0: y = 0; vy = 0`; then `x` and `z` are **clamped** (not bounced) to
   `[-arena, +arena]`.
7. collection, after the move: for each orb not yet taken, with `dx = x-ox`, `dz = z-oz`,
   collect when `dx*dx + dz*dz < 1.2*1.2` **and** `y < 1.5`. `collected` is a bitmask,
   orb `i` is bit `i`. An orb is never released once taken.

**Orb placement (LCG, both languages).** `s = seed & 0xFFFFFFFF or 1`; `span = arena*0.8`;
then per orb **two** draws, `x` first: `s = (s*1664525 + 1013904223) & 0xFFFFFFFF`, and the
coordinate is `((s/0xFFFFFFFF)*2 - 1)*span`. No `Math.random()`, no re-seeding.

**The hashed string, byte for byte.** `"%.4f,%.4f,%.4f,%.4f,%.4f,%d" % (x, y, z, vy, 0.0,
collected)` — four decimals, comma with no space, **no trailing separator and no newline**.
The fifth float is a reserved slot that is always `0.0`; it is in the string, so a port
that omits it and a port that fills it with something else both disagree. Nothing else
enters the hash: not the tunables, not `difficulty`, not tick count, not the shard id.

**The digest.** Two 32-bit FNV-1a lanes over the UTF-8 bytes of that string, in order:
`h1 = 2166136261`, `h2 = 84696351`, each byte `h = (h ^ byte) * 16777619 mod 2^32`. Output
is `"%08x%08x" % (h1, h2)` — lane 1 then lane 2, eight zero-padded hex digits each, lower
case. Total 16 characters.

A port that implements exactly this reproduces `1f046312729509fc` for `highend_duel`
without reading `shardex.py` or the page (proved by `tests/test_third_impl.py`, 2026-11-02).
`1c045e596f950543` needs one more input: the tournament-surface config below, not the
shard. The test pins both so neither number can be quoted as the other.
What that proves is **sufficiency of the specification, not independence of the authors**:
the law above was transcribed from the reference, so a misreading shared by all three is
still possible. Only a stranger writing from this page alone would retire that.

## The tournament surface (what a champion actually touches)

```json
{ "sim_hz": 60, "gravity": 18.0, "speed": 6.0, "jump": 7.0,
  "arena": 8.07, "orbs": 3, "difficulty": 1.12, "seed": 4220286397 }
```

Those are the tunables that produced `1c045e596f950543`. They are **not** what the clone
derives today (8.06 / seed 3926918967 / difficulty 1.08), so a champion reading this block
and a tool reading `flame.json` disagree about the arena. Both readings are recorded; only
the derived one is traceable to the artifact's own bytes, and only the derived one is what
`--forge` writes.

**Not every field moves the hash, and the claim used to say every one did.** Measured
2026-11-02 on the clone: `gravity` 18 → 24 → 32 leaves the digest at `1f046312729509fc`,
and so does `jump` 7 → 10, because the scripted run ends back at the origin with the
vertical cancelled. `speed` moves it only once the walk exceeds `arena` and the clamp
bites (6.0 → `1f046312…`, 9.0 → `7bf3c77f…`). What the clone's hash actually reports is
**which orb was touched** — the state is `-0.0000,0.0000,0.0000,0.0000,0.0000,<mask>`, so
the reachable digest space for this artifact is eight values. A bracket may publish a
config and a hash anyone can reproduce, but the hash is a 3-bit witness, not a fingerprint
of the arena's physics: `tests/test_third_impl.py` pins that, so it cannot be quietly
claimed back. `--verify` recomputes independently and refuses a bundle whose
claimed hash does not recompute, whose shell still carries `__FLAME_JSON__`, or whose
shell does not name its own shard.

The determinism partition from `docs/METTHEW/shard.schema.json` is respected in the only
way this tool can respect it: **the hash covers sim state, never a frame.** Lighting,
glow and the camera are presentation and are not in the hash.

## Refusals, and the incident each one prevents

| refusal | what it stops |
| --- | --- |
| a source that is not a directory → exit 2 `NO-SOURCE` | an empty mirror reported as a small game |
| a source with no files → `EMPTY-SOURCE` | "0 files" read as a setting |
| payload over the cap → shard `REFUSED` with the byte count | a shard that fails the validator later, when nobody remembers which slice it was |
| a shard with no entrypoint → `NO-ENTRYPOINT` | forging an arena from nothing, and calling it a game |
| a slice cited as a game → `state: SLICE`, `golden_run` all zeros | the word "game" doing work the artifact has not earned |
| `--verify` on a golden that does not recompute → `REFUSED` | a bundle that lies about being the bundle that was proven |

## What is next (and what would be dishonest to promise)

1. **Ruleset extraction** (L4, research): recovering movement, collision and win
   conditions from a game's code. Until that exists, no document here says "your game".
2. **Signed results**: `author_pubkey` is in the schema and empty in every forged
   manifest. A result file that anyone can edit is a result file nobody can rank.
3. **A composed arena in a browser**: `--compose` merges the meshes and names the set, and
   `meshscene` renders a single mesh; the merged mesh has not yet been driven through the
   page, so L5 is a name and a digest, not playable.

### Ranked brackets (L4, 2026-11-02)

`rank.py` ranks a bracket's results rather than only replaying them: single-elimination and
round-robin, a winner decided by score then hash (never by input order), and a result file
that `--verify` re-derives — a hand-edited round hash or winner is refused.
`python Project_SHARDEX/rank.py --selftest` → 13 checks, `selftest: PASS`, including
"perturbing any one entrant's golden hash moves round 1's hash (8/8)" — the round hash is a
function of every entrant, which is what L4 was missing when a bracket could rank nothing.

### Composing two arenas (L5, measured 2026-11-02)

```
python Project_SHARDEX/shardex.py --compose build/tmp/r4/arena build/tmp/r4/moved
  lane 0  1894f7d8c9908126   576 neurons, 1108 synapses  offset 0
  lane 1  a478063c575874f2  1152 neurons, 2309 synapses  offset 192
  merged       1728 neurons, 3417 synapses, grid 384x54
  mesh digest  226d539422b9202a
  composition  6ff14820ed418db8
```

The two arenas are not made commensurable by being merged: each keeps its own mesh digest
and is placed at an offset, and the composition hash is taken over the **sorted** input
digests, so `--compose a b` and `--compose b a` name one space (`tests/test_compose.py`,
9 tests). A rule the inputs disagree about (`sim_hz`, `ticks`, `seed` differ between the
two reference shards) is **refused** until it is declared, and a declared value must be one
an input already states — a silent average would be a third arena nobody authored.

## Intake: when a real game tree arrives (SHX-7 / SHX-8)

The selftest fixture is four files. A real tree is where the heuristics fail, so the
intake is a documented run, not a vibe:

```bash
python Project_SHARDEX/shardex.py --mirror <game> --out .shardex
python Project_SHARDEX/shardex.py --shatter --mirror-file .shardex/mirror.json --out .shardex
python Project_SHARDEX/shardex.py --forge .shardex/shards/<one> --out flame
python Project_SHARDEX/shardex.py --verify flame
```

And the record must answer, in numbers: how many files and bytes were seen (and how many
were skipped, with names); how many groups became shards; how many shards were refused and
why; which shard was forged and its golden hash; and whether headless Chrome printed that
same hash. A second identical run must produce byte-identical shard ids — if it does not,
the pipeline is reading something it does not declare.

What is expected to break, listed so a fix is measured rather than improvised: a game whose
whole logic sits in one directory (one giant group), non-UTF8 or over-long Windows paths,
symlink loops, duplicate basenames collapsing inside one shard, asset directories that
dominate the payload, and shards whose entrypoint is a shader or a data file rather than
code. **The low-end ceiling is not raised to make a tree fit** — the ceiling is the
contract the validator enforces, and moving it turns a measurement into a preference.

**First real-tree run (2026-11-02, `tools/swarm_arena`, 25 files / 4.5 MB on disk).** The
measured numbers, and the one defect the run found:

| reading | value |
| --- | --- |
| files mirrored | 12 (3 063 947 bytes; 4 code, 0 asset, 8 data) |
| files silently not mirrored | **13 files, 3 024 915 bytes — 98.7% of the tree's bytes** |
| `skipped` field | `[]` |
| groups → shards | 4 groups; `swarm-arena` (4 files, 10 269 B), `judge-rs` (3, 6 984 B), `out` (2, 12 609 B) |
| refused | `judge-go`, payload 3 034 085 > cap 2 097 152 — the ceiling working as declared |
| determinism | two `--shatter` runs produced an identical shard set (same 3 ids, same hashes) |

The defect is the third row. `SKIP_DIRS` pruned `judge_rs/target` — correct, it is build
output — but the mirror recorded the prune nowhere: `skipped` only ever held files that
failed `stat`, so the document claimed nothing was skipped while 13 files were gone. A
reader comparing 12 against the tree's 25 could not tell a deliberate exclusion from a
walk that died. The mirror now carries `pruned` (path, reason, files, bytes, `unreadable`) and
`not_mirrored` totals, and prints them. `unreadable` is there because a subtree entry that
cannot be `stat`ed was skipped from the count without a word, which let `pruned` report a
pruner that took less than it did — the same defect one level down:

```
  NOT MIRRORED: 1 dir(s), 13 file(s), 3024915 bytes (judge_rs/target)
```

So the intake now answers the question in numbers without a second walk, and the
`--shatter` determinism test below is unchanged because the exclusion is still stable.

## Transubstantiation: a 2D animation becomes a 3D one (SHX-6, narrow slice)

`shardex.py --forge` generates an arena *from* a shard: its own `fidelity` field says the
original rules are not extracted. `transubstantiate.py` is the other direction and does one
thing: read a 2D canvas animation, **extract the rules that make it move**, and emit a 3D
scene obeying the same rules on the same clock.

```bash
python Project_SHARDEX/transubstantiate.py --extract <animation.html> --out .transub/rules.json
python Project_SHARDEX/transubstantiate.py --forge .transub/rules.json --out .transub
python Project_SHARDEX/transubstantiate.py --bind-shard .transub/shards/<id>/shard.json \
        --forge .transub/rules.json
python Project_SHARDEX/transubstantiate.py --predict .transub/rules.json
NODE_PATH=$(npm root -g) node tools/capture_transubstantiation.js .transub 240
python Project_SHARDEX/transubstantiate.py --verify .transub
python Project_SHARDEX/transubstantiate.py --selftest
```

**The extraction contract is five rules, and a missing one is a refusal, not a default.**
A deterministic clock (`window.__step(ms)` or `draw(p)`), phase constants (`GROW`/`LABEL`/
`HOLD`), a seed (`mulberry32(<int>)`), an entity table (`LIMBS = [["name", side, spread,
"#hex", "path"], …]`), and a root `branch(...)` call with a length-shrink expression. Each
extracted rule records the **line that proves it**. `--selftest` runs a positive fixture, a
negative control (a source with no clock, which must be REFUSED) and a tamper check.

**What verification actually checks is a differential between two implementations.**
`golden3d.json` holds a quantised geometry digest and the projected state at three ticks (one
in GROW, one in LABEL, one in HOLD). `capture_transubstantiation.js` reads `window.__geo()`
and `window.__state(tick)` from the live page and writes `browser_probe.json`; `--verify`
refuses when the two disagree. That refusal earned its keep on the first run: the Python port
of mulberry32 was wrong (476 segments against the browser's 489), then the digest stream was
wrong (`%.4f` vs `toFixed`, and a `|`-joined list against a `|`-suffixed one). Both were
found by the cross-check and by nothing else.

Measured on `docs/YGGDRASIL_CLEAVE.html` (sha256 `81e1dabe48223b87…`, 10 limbs, seed
20261028, 30 000/8 000/7 000 ms): **489 segments, 822 leaves, geometry digest
`69b9d1ad4c93d173`, browser cross-check MATCH**, 240 frames → 1920×1080 H.264, 3.6 MB, 24 fps,
decoded and read back. The `*.mp4` and the frames are gitignored local artifacts; regenerate
with the four commands above.

**Fidelity, stated rather than implied:** phases, seed, entity table and branch law are
carried with evidence. No pixel, colour ramp, sprite or label is carried. In 3D the limb
`spread` rule becomes the outward tilt of a ring around the trunk, because the 2D source fans
limbs across the single axis it has; that mapping is a documented interpretation, not an
extracted constant.

### L3 — a rule that cannot be wrong is a label, not a finding

Extraction records the **line that proves a rule is present**. Presence is not causation: a
constant can be declared, cited, and never read by the motion. `--predict` closes that gap
without executing the page — it perturbs the rule, states the observable change the original
animation must show, and measures that observable at the rule's **use site** in the source,
re-derived from the source's own declarations rather than from the extracted JSON (a
measurement that borrows the value it tests cannot disagree with it).

```bash
python Project_SHARDEX/transubstantiate.py --predict .transub/rules.json
```

Three outcomes, and the middle one is deliberately not a pass: **VERIFIED** (the use site
carries the value and the perturbation moves the observable by the predicted amount),
**FALSIFIED** (the source contradicts the rule), **PRESENT-BUT-UNFALSIFIED** (there is no
observable in the source to measure, so the rule is scored as neither). Fewer than 3 of 5
verified is a REFUSED run.

Measured on `docs/YGGDRASIL_CLEAVE.html` (sha256 `81e1dabe48223b87…`): **3/5 verified**,
and the two non-passes are the interesting part.

- `phases` — **FALSIFIED, and it found a defect in the animation.** `GROW += 1000` moves the
  governed boundaries `p<GROW` and `p<GROW+LABEL` by exactly +1000 ms, so the constant is
  live in the motion. But line 220 tests `p<9000` — a literal inside the 30 000 ms GROW
  window — so "growing the trunk…" ends at 9 s while the trunk is still growing for another
  21 s, and the branch text at line 221 fires for the rest of the growth. The caption ladder
  does not follow the clock it is captioning. (Left unfixed here: it is the evidence that
  the oracle can fail. The one-line repair is `p<GROW`.)
- `branch` — **PRESENT-BUT-UNFALSIFIED.** `branch()` recurses with `len*(.68+R()*.12)`; the
  law is present, but the segment count is produced by canvas calls at runtime and no number
  in the source states it, so there is nothing to measure without executing the page. Scored
  as neither rather than counted as a pass.
- `clock`, `seed`, `entities` — VERIFIED. `ms` reaches `draw()`; `mulberry32(20261028)` first
  draw is `0.064762334` against `0.850172859` at seed+1, so a bearing change is predicted and
  `R()` is shown consumed inside `branch()`; the source `LIMBS` table holds 10 rows and the
  render loop iterates it, matching the extracted table.

**The oracle has a control.** The same source with `draw(ms)` removed from `window.__step`
(so the hook sets the clock and never paints) scores **2/5 and REFUSES**, with `clock`
FALSIFIED naming `set / NOT drawn` ("assigned into the clock: set; passed to draw(): NOT
drawn"). A predictor that only ever emits VERIFIED is not
evidence, so this control runs alongside the positive one.

## Live mutation: an image becomes a mesh, and the mesh changes while it renders

`transubstantiate.py` translates a program whose rules are readable. An image has no rules to
read, so the honest representation is **sampled data plus a graph that moves**, and the graph is
mutated by operators applied to a scene that is already running.

```bash
NODE_PATH=$(npm root -g) node tools/sample_image.js --in <image> --out .live/field.json
python Project_SHARDEX/meshscene.py --forge .live/field.json --out .live
NODE_PATH=$(npm root -g) node tools/capture_transubstantiation.js .live 180 \
        --live .live/ops.json
python Project_SHARDEX/meshscene.py --verify .live
```

**Pipeline.** Image → field (`96x54` luma/hue/Sobel, sha256 of the source, plus a 256-entry Q15
sine table) → mesh (`576` neurons, `1201` synapses for a 640×480 photograph) → scene with one
mutation entry point, `window.__mutate(op)`.

**The operators** (`ops.py`): `warp`, `sprout`, `prune`, `palette`, `extrude`. Each is a pure
function of (mesh, op); each exists twice, in Python and in the page; each op's digest is
recorded by the page *after* it applies, and `--verify` replays the log and must reproduce every
digest. Measured on 2026-11-02, applied between frames 30/60/90/120/150 of a 180-frame render:

| seq | op | mesh digest | neurons/synapses |
| --- | --- | --- | --- |
| 0 | warp amp 3.0 | `51fdace00bdd1bfe` | 576 / 1201 |
| 1 | extrude ×3 | `9c89b09f0553e46d` | 576 / 1201 |
| 2 | palette +120° | `b799871e7759a070` | 576 / 1201 |
| 3 | sprout 300 | `a37949c2ead7f094` | 576 / 1501 |
| 4 | prune <0.6 | `1894f7d8c9908126` | 576 / 1108 |

`--verify` → VERIFIED, op chain `d23155c2cf6a8324…`, all five digests reproduced in Python, base
mesh and three projected golden states matching the page exactly.

**Three defects came out of this build, all of the same shape** — a measurement that disagreed
while the thing being measured was correct. The projection quantised at 1e-2, then at 1e-4, while
the page used 1e-3; the base mesh digest matched all along, so only the states failed and only
three of them. The lesson is written into the code: when a digest compares two implementations,
the ruler is part of the contract.

**Two gates, both measured.** `FLAT-FIELD` refuses a field whose *mean edge energy* is under 6.0
(the first gate used `std(luma) >= 40` and refused every dark UI panel in this tree while
accepting a solid fill); a solid fill measures 0.0, panels 8.2–17.3, a photograph 32.6. And
`OP-INVALID` refuses an operator carrying a field it does not use, because an ignored parameter
is a mutation that quietly did less than its author believed.

**Fidelity.** The mesh is a *representation of the sampled field*, not a reconstruction of the
image: no pixel is drawn, and the neurons sit on a block lattice. What is carried is structure
(where edge energy was), colour (sampled hue per cell) and relief (luma as depth) — and what is
verified is that both implementations agree about every one of those after each mutation.

## A question this pipeline has to answer honestly: images, and mid-flight mutation

> Could a shard be built from a **single image**, and could modifications — morph, mutate,
transmogrify — be applied **mid-flight** while it renders?

Mirroring an image directory already works (`--mirror` classifies `.png`/`.jpg` as `asset`
and carries it for provenance, never executes it). Everything after that is unbuilt, and the
honest answer separates the three parts:

1. **Image → rules.** A new extractor (`shardex-image-rules-v1`), because the current
   contract is a *clock and a branch law* and an image has neither. It needs a height field
   (luminance or edge energy on a grid), a palette from quantised hues, and a symmetry axis.
   No new dependency is required: the capture harness already runs Chromium, so the decoder
   is `drawImage` + `getImageData` in the page and the field arrives as JSON.
2. **Mid-flight mutation.** This is the part the current scene *nearly* has and does not:
   `draw(p)` is a pure function of tick, so a mutation layer would sit between tick and draw
   as `{at_tick, warp, palette_shift, scale, spin}` and be **golden-hashed like the base
   scene** — a mutation that cannot be verified is a change nobody can review. Nothing writes
   into a running scene today; changing the scene means re-forging it offline.
3. **Fully rendered.** Already true, and measured: the tick clock is driven from outside the
   page, so 240 frames encode to H.264 and decode back. "Fully rendered mid-flight mutation"
   is one layer above a renderer that already works.

So: possible, half-built, and the half that exists is the hard half (determinism, golden
hashes, refusal, cross-language verification). Treat the image extractor and the mutation
seam as the next increment, not as features.
