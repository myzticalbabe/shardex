# Disclosure Policy

## Purpose

This policy governs how Project SHARDEX handles sensitive information
that may be encountered during codebase mirroring, shattering, and
forging into a FLAME arena.

## What We Do Not Distribute

Project SHARDEX **does not distribute**:

- Raw source code from mirrored codebases (unless explicitly allowed by the codebase's license)
- Secrets, API keys, credentials found during mirroring
- Proprietary algorithms or business logic from mirrored codebases
- Generated artefacts (`flame/`, `.shardex/`, `.transub/`, `.live/`, `*.mp4`) — these are gitignored and regenerated by commands
- Any material about identifiable individuals that is not already public

## What We Do Distribute

- The pipeline **METHOD** (mirror, shatter, forge, transubstantiate, verify)
- Open-source tooling for content-addressed sharding and FLAME arena forging
- Documentation and examples using synthetic/public codebases
- Configuration templates

## The Honest Boundary

SHARDEX does not extract a game's rules. It derives a deterministic
arena from a shard's own content hash and provides a golden state
hash that independent implementations must agree on. SHARDEX.md's
"honest boundary" section governs what may be claimed.

## Handling Sensitive Data in Mirroring

If mirroring encounters sensitive data (secrets, keys, PII, proprietary code):

1. **Stop** — do not commit, log, or include the sensitive data in shards
2. **Redact** — remove or hash the sensitive identifiers before shattering
3. **Report** — notify the project maintainers via security@azazael.local
4. **Verify** — ensure the forged arena would not leak sensitive data
